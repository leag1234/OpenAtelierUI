# Trusted-header identity compatibility prototype

This bounded candidate change addresses the observed empty-profile trusted sign-in gap. It adds an opt-in-by-configuration `WEBUI_AUTH_TRUSTED_ROLE_HEADER` name, default unset. When both the existing trusted-email header and role-header name are configured, a new identity is provisioned only from exactly one valid email and one explicit supported role. This role-aware path does not use public signup or change login/signup configuration.

The role-aware path accepts only explicit `user` or `admin`; an explicit trusted `admin` assertion may provision the first account. No missing or invalid value is defaulted to administrator. `pending` and unknown role values are refused for new identities because those provisioning outcomes were not measured. Existing identities are authenticated by their stored account record; the incoming role value never updates or overrides their stored role. If the role-header name is unset, the pre-existing trusted-email path is retained, including its public-signup gate and first-user default-role behavior. The role-aware policy is therefore opt-in and is not a general proxy-trust mechanism.

New account creation uses the existing `Auths.insert_new_auth` model path with a random password that is hashed before storage. Email, role, and configured display-name shape are validated before this call. Invalid/missing/duplicate values perform no insert in the isolated route tests. No proxy secret or general proxy trust mechanism was added.

## Checks and limits

`python3 validation/test_trusted_header_identity.py -v` executes the actual extracted helper, signin, and public-signup functions with isolated in-memory account stubs. It covers first ordinary-user creation with public signup and login disabled, explicit first-admin provisioning under the configured role header, existing-role preservation, missing/duplicate/invalid email or role, the legacy trusted-email signup gate and first-user default when the role header is unset, disabled public signup, and the unconfigured password-signin path. These tests do not exercise FastAPI dependency wiring, SQLAlchemy transaction behavior, proxy trust boundaries, cookies through an HTTP client, or cookie/Bearer precedence. The primary's isolated native proof is still required.

Unknown behavior is not generalized: pending-role provisioning is refused; no production proxy authentication or secret validation is claimed; races between parallel first-user requests and model-level multi-table rollback remain unqualified. Signup defaults, API-key issuance, session validation, existing user roles, and non-trusted signin routes were not changed.

The first run of the existing `backend/open_webui/test/test_session_epoch_auth.py` harness exposed omitted AST namespace bindings for `_VALIDATED_API_KEY_STATE_ATTRIBUTE`, `_VALIDATED_API_KEY_STATE_MARKER`, and `is_validated_api_key_request`; trusted signin extraction also did not include the new helper or a header object with `getlist`. That failed receipt is retained in the work log. The test-only extraction namespace was corrected to bind the actual existing state-marker function/constants and the new helper; no auth runtime behavior was altered for the harness. The rerun passes all 23 cases.

Primary review corrected two candidate assumptions before native proof: an explicit configured `admin` role is intentional (not accidental elevation), while an unset role-header must retain the legacy trusted-email/signup path. The isolated route test now covers both behaviors. An initial compile command also hit the environment's unwritable default bytecode cache; rerunning with `PYTHONPYCACHEPREFIX` succeeded.

Focused local results: `python3 validation/test_trusted_header_identity.py -v` passes 7 tests; `python3 validation/test_api_key_user_permission.py -v` passes 3 tests; `python3 backend/open_webui/test/test_session_epoch_auth.py -v` passes 23 tests. Bytecode compilation with a temporary cache and diff whitespace checks pass. Native app proof remains primary-owned.
