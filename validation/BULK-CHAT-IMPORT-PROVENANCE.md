# Bulk chat import prototype provenance

This bounded candidate change adds the measured `{ "chats": [...] }` form to the existing chat import endpoint through an explicit `ChatsImportForm` DTO. The existing typed `ChatImportForm` singleton still calls `Chats.import_chat` with its original per-chat behavior and response; missing singleton `chat` is rejected by normal request validation. Bulk entries use a strict DTO for known fields, then the bulk path always assigns new UUIDs and the authenticated caller as owner, sets sharing/folder/archive state to private defaults, preserves the submitted graph and integer timestamps, and commits all rows together.

The accepted profile is 1–16 chats, at most 4 MiB of serialized input and 4096 message nodes total. The prototype rejects unknown form fields, nonempty metadata, files/attachments, folders, shared or archived input, malformed timestamps and a selected message that is absent from the graph before opening the database session. Structured image/media content, tool-role messages, tool-call records and non-text content blocks are refused rather than copied under a text-only label. Tags and other metadata effects are not imported. A second-insert failure rolls back the entire batch. Existing source IDs and submitted owner IDs are ignored; each result is a new private copy owned by the verified caller.

`python3 validation/test_bulk_chat_import.py` runs nine source-extracted checks with installed Pydantic 2. They execute the actual DTOs, preparation function, route dispatch and model method body against a fresh in-memory SQLite transaction adapter, including two-item success, owner/ID/timestamp/branch assertions, a SQLite trigger that rejects the second row, pre-session media/profile refusals, each measured nullable default separately, bulk array routing, strict bulk fields and unchanged typed legacy dispatch. The host does not have SQLAlchemy installed, so these checks do not qualify SQLAlchemy session behavior or a mounted HTTP app. The primary-owned independent real SQLAlchemy/HTTP replay remains necessary.

Primary review rejected initial source77 before runtime staging because its dictionary request parameter removed the typed request DTO and allowed structured media content through the attachment-only check. That commit remains intact; source78 restores named DTOs and text-only checks. The separately observed current01 cases permit `pinned:null` as false, `variables:null` as absent, `current_message_id:null` as the inner graph selection, and `created_at:null` or `updated_at:null` as generated timestamps. Tests cover each field individually, not in combination. Explicit `meta:null` and `archived:null` remain refused. No broader nullable-form behavior is inferred.

The final source76-to-source79 runtime diff is 124 gross added nonblank lines and 4 removed nonblank lines, within the 160-line cap. Source78 alone measured 117 additions and 4 removals; this follow-up adds seven nonblank lines. A previous helper message reported 136 accumulated gross additions as the final diff; that count was incorrect and is superseded by this direct baseline diff count.

The first `py_compile` attempt used the host's protected default bytecode-cache path and failed with `PermissionError` before compiling sources. Re-running with `PYTHONPYCACHEPREFIX=/tmp/bulkchat-pycache` passed; no repository bytecode or source was changed by that failed attempt.

Measured current behavior is limited to the supplied synthetic current03 observations: array request and array response, private ownership, distinct copies on replay, graph/selected-answer preservation, and useful saved continuation. Folders, tags, attachments, shared imports, other metadata, broad response compatibility and production-scale resource behavior are unsupported or unqualified. This is an isolated compatibility prototype, not full API or operating-system certification.
