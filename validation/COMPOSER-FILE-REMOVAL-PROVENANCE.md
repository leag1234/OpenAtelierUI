# Composer file-removal lifecycle

The Round 12 unchanged-integration report reproduced one intermittent 404 after two uploaded files were removed immediately before the first message. The existing composer waited for each server-side file deletion before updating its local `files` array. A prompt submitted during that await could therefore snapshot a file descriptor whose persisted row had just been deleted. The authenticated completion correctly rejected that stale descriptor with a generic 404.

The correction detaches the selected item from the local immutable array before awaiting its existing owner-scoped deletion request. It does not change the deletion endpoint, file authorization, completion authorization, chat ownership or error response. Two rapid clicks address the current first item twice; because local state changes synchronously, the second click selects the next remaining item even before the DOM rerenders. A deletion failure can leave an unreferenced upload for ordinary cleanup, but it cannot reattach the descriptor or send a deleted reference. No content, filename, user identity or credential is logged.

`validation/test_composer_file_removal.mjs` runs the actual helper, verifies ordered removal of two descriptors without mutating the input array, covers four invalid indices, and binds the Svelte handler to the required detach-before-await ordering. The existing source suite keeps missing and foreign file/chat references as generic 404 responses before provider effects. Exact-image repeated browser and API qualification remains owned by the primary campaign; this component test alone is not a browser or universal compatibility claim.
