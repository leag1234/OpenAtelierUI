# Explicit async model compatibility spike provenance

This is a default-off adapter for a later fresh-volume evaluation. It changes no HTTP route, database model, configuration default, auth behavior, or dependency. It does not establish Atlas compatibility or product readiness.

`run_verified_bootstrap(script_path, expected_sha256, args=())` is the explicit launcher entry point in `open_webui.utils.async_model_bootstrap`. It accepts only a regular non-symlink file whose bytes fit within 1 MiB and match the supplied SHA-256. The exact bytes read and hashed are sent over stdin to a new child process; later path changes cannot replace those bytes. Arguments are separate argv strings, no shell is used, and stdout/stderr are discarded. The child imports the existing application config before executing the selected script, temporarily proxies only the six named Functions/Models calls with `asyncio.to_thread`, and restores the original module bindings on normal return or exception. Nonzero child status is returned without script output or exception text. This is an explicit script execution feature, not a sandbox; the operator-selected script runs with the child process's ordinary application privileges.

`adapt_filter_module` extends the existing task-local Filter SDK bridge. Direct singleton aliases and exact dynamic imports of `open_webui.models.files` / `open_webui.models.chats` receive module-local views that adapt only `Files.get_file_by_id` and `Chats.get_chat_by_id_and_user_id`. Async handlers receive worker-thread awaitables; sync handlers and constructors retain native synchronous values. The wrappers preserve positional/keyword arguments, return values, `None`, and exceptions, including the existing caller-supplied chat owner ID. Other attributes and imports delegate unchanged. The adapter does not replace process-wide model attributes or `sys.modules`; wildcard imports are left untouched. `utils/filter.py`'s existing task-local mode/reset is reused, including reset after error or cancellation.

Focused validation: `validation/test_model_async_compat.py` passes six tests covering all eight selected plugin/model methods, off-loop calls and a heartbeat, `None`/error propagation, direct and aliased imports, exact dynamic imports, non-target imports, synchronous mode and unchanged process modules, script path/hash/size refusal, verified-byte use after a path change, child config-import ordering, and singleton restoration. Existing `validation/test_filter_sdk_compat.py` passes eight tests, `validation/test_filter_priority.py` passes seven, and `validation/test_plugin_load_preservation.py` passes four. Python compilation of the four admitted runtime modules and the new test passes; `git diff --check` passes.

One first draft imported Files/Chats on every Filter load. That broke two existing isolated loader tests whose namespace intentionally lacks application modules. The loader now activates compatibility only when a Filter module has a relevant direct singleton/module or importlib binding; target modules resolve lazily for dynamic lookups. The retained correction avoids extra module imports for unrelated legacy Filters.

No external bootstrap was executed. Tests use synthetic modules and a mocked process boundary; they do not establish actual application database behavior, installed-plugin compatibility, Python deployment compatibility, task cancellation semantics of every native SDK caller, or an isolation/security boundary for selected code. Unsupported import patterns include wildcard interception, copied/re-exported APIs outside the selected module bindings, dynamic aliases other than the exact observed module paths, and non-listed model methods. Existing asynchronous Filter dispatcher behavior is reused; broader plugin types and arbitrary imports remain unqualified.
