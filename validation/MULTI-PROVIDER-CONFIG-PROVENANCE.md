# Bounded multi-endpoint configuration import

This follow-up extends the existing default-off `--include-openai-configuration` importer selection to preserve one through eight distinct endpoint URLs and an equal-length indexed API-key list. URL/key order is retained exactly; reusing a key for separate endpoint entries is accepted. The old target configuration mapping, pinned defaults, selector composition, report shape, prototype blocker, and `cutover: false` behavior remain unchanged. At the initial multi-endpoint slice, only an empty options object was accepted. The later measured provider-enable slice also accepts a complete canonical endpoint-index map whose sole field for every index is a strict JSON boolean `enable`; it preserves explicit true and false values. Sparse maps and every other options field remain refused. The parser still requires an enabled top-level JSON boolean, credential-free bounded HTTP(S) URLs, and bounded nonempty ASCII keys. Duplicate endpoint strings, unequal or out-of-range lists, and malformed entries fail before target creation without including values in diagnostics.

The measured current 0.12.4 fixture used exactly two distinct loopback endpoint prefixes and two synthetic keys, with two own public-read models. Its frozen client checked discovery, indexed fake-key routing, selected plain/SSE replies, existing user-key/password behavior, and access denials. That is evidence for this specific two-endpoint journey only; unit coverage for three through eight entries is parser/conversion-boundary coverage and does not qualify native behavior for those counts or arbitrary providers.

Focused tests cover two-entry ordered conversion, key reuse, the eight-entry limit, empty/unequal/duplicate/over-cap/malformed URL lists, default-off behavior, existing selector composition, indexed enable-state preservation/refusals, and key redaction. At the prior multi-endpoint commit the focused file had 10 passing tests; the provider-enable follow-up adds specific complete-map and hostile-map coverage. The independent primary CLI/source/runtime replay remains separate from these local tests. The general importer suite had 51 tests, with the existing API-key and user-permissions suites at 7 and 8. An initial combined `unittest` module-name invocation ran zero tests because these scripts import sibling modules by bare name; the corrected direct-script commands from the candidate root executed the tests and passed. Repository-wide `tools/check_repository.py` is located at the monorepo root rather than this isolated candidate checkout and must be run there by the primary integration owner.

This importer does not contact endpoints, enable provider runtime behavior, add schema/dependencies, migrate nonempty options or advanced credentials, or remove remaining configuration blockers.
