# Plugin event routing compatibility prototype

The primary's measured own async-Pipe journey showed ordered progress on `chat-events`, but a member-supplied foreign session ID received both progress and final reply in the source64 candidate. The measured current 0.12.4 service delivered those events only to the requesting member and ignored the foreign SID; its useful member reply continued. Other acknowledgement/status/task-ID and lifecycle differences are outside this first slice.

`backend/open_webui/socket/main.py:get_event_emitter` now considers only the existing request user's `USER_POOL` SIDs plus the requested SID, and emits only to entries whose existing `SESSION_POOL` record is a dictionary with matching `id`. Invalid or empty request user IDs produce no recipients. It does not query the database or perform auth/credential lookup. The same authorized envelope is emitted once on the native `chat-events` channel and once on the legacy passive-listener `events` channel for each eligible session. This default is required by the measured unchanged integration: otherwise it misses terminal completion and marks already completed turns as interrupted after a reconnect. Interactive event calls still select exactly one response channel. Existing event payloads and `update_db` status/message/replace processing remain unchanged.

Four focused source-extracted tests exercise foreign/stale/malformed session entries, duplicate requested/pool IDs, valid same-user multi-tab routing, invalid user IDs, dual-channel envelope identity, and one status DB update. They execute the actual `get_event_emitter` function body with fake in-memory pools, socket emitter, and chat store; they do not import or run the full application or establish Socket.IO transport behavior. The exact-image Atlas journey supplies the transport/reconnect evidence.

The alias doubles passive event serialization for each authorized destination; the source test does not establish a per-completion byte/latency budget. Interactive callbacks, cross-process Redis semantics, HTTP acknowledgements, tasks, notification delivery and human comprehension remain separately bounded. This does not broaden recipients, create a new trust path or establish exhaustive event compatibility.
