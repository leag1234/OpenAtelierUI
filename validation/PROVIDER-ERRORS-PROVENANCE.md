# Bounded provider-error response prototype

The candidate gateway maps upstream provider failures to HTTP 400 and loses the measured error code. The own current 0.12.4 fixture returned HTTP 401, 429, and 500 for both plain and streaming requests, with an `application/json` body containing only the top-level `error` object (`message`, `type`, and `code`). The paired source62 native Fire/Venus comparison flattened all six responses to 400 with a string `detail`. A following valid request and anonymous denial remained correct. These are own synthetic fixture results, not arbitrary-provider qualification.

This default-off prototype is enabled only by `OPENATELIER_PROVIDER_ERROR_COMPAT=1`. In `backend/open_webui/utils/provider_errors.py`, `build_provider_error_response` bounds the body read to 1 MiB, accepts only HTTP error statuses 400–599 and strict UTF-8 JSON containing only an `error` object with bounded string `message`, `type`, and/or `code` fields, then returns a marked `ProviderErrorResponse`. Invalid status/body/field shapes use a generic sanitized JSON error. The helper redacts the already-selected provider key and request bearer token from every returned string; it makes no credential or database lookup. `routers/openai.py` uses this path only for upstream error statuses when the flag is set. `main.py` returns that own marker before normal success processing. Successful calls and the existing flag-off error path remain unchanged.

Local controls cover opt-in behavior, the measured status/envelope projection for plain and stream modes, redaction, malformed UTF-8/JSON, duplicate keys, non-finite values, invalid UTF-8 surrogate strings, unsupported fields/types, oversized bodies/fields, invalid statuses, and the outer handler's typed bypass ordering. The seven-test file is run as `PYTHONPATH=backend /usr/bin/python3 validation/test_provider_error_projection.py`; it uses installed FastAPI/Starlette response primitives and source-AST verification, not a running application. The first local run found two correctable issues: an unsupported extra field was mistakenly included in a positive test, and invalid status fallback still projected a valid body. Both were fixed, and the focused suite passes seven tests. Primary independent source/component and unchanged-client replay remains required.

This prototype does not qualify other status codes, error fields, custom content types, arbitrary providers, oversized/streaming error bodies, or general stream behavior. It does not change auth, model selection, success hooks, dependencies, schema, defaults, or credentials. It is not a production error-handling or security certification.
