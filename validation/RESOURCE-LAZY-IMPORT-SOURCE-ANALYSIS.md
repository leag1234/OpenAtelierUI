# Old-BSD lazy-import source analysis

## Boundary and measured baseline

This notes-only scan used the bounded worker brief and the frozen old BSD candidate source. It did not inspect current implementation bodies, primary history, acquisition/quarantine archives, or other evidence. It changed no application code, dependency, schema, route, or default.

The primary-provided no-provider idle profile reports PSS 744,189,952 bytes and RSS 749,576,192 bytes, above the provisional 512 MiB PSS target. Five-minute idle CPU was 0.08667% of one core. File mapping groups report torch PSS 74,354,688 bytes, numerical libraries 52,211,712 bytes, other files 104,620,032 bytes, and anonymous mappings 512,823,296 bytes. These are aggregate mapping groups, not Python-module heap attribution. The single 30-request batch p50 12.5845 ms / p95 21.3514 ms is noisy and supports no latency comparison. This source scan makes no estimate of savings and does not assign anonymous memory to Torch or any import candidate.

## Checkable candidates

1. **Import only the selected web-search adapter.** `backend/open_webui/routers/retrieval.py:43-63` imports eighteen provider modules eagerly; `search_web` dispatches to only the configured engine at lines 1265-1465. The retrieval router is imported through `backend/open_webui/main.py:55-85`, and is also imported by middleware, files, and knowledge modules, so this graph is active even for ordinary no-provider chat. A later isolated spike could move each provider import into its matching dispatch branch after existing validation/credential checks. Compare cold module/import-time traces and five-minute idle PSS with a saved web-search request to one selected provider. Check that unselected modules stay absent, all selected-engine outputs/errors and credentials remain identical, route/auth behavior is unchanged, and first-use delay is acceptable. Risks: import failures move from startup to request time; a refactor could import the wrong adapter or change error ordering. This is the narrowest direct startup-import hypothesis.

2. **Load document-ingestion and retrieval helpers on their operation path.** `backend/open_webui/routers/retrieval.py:26-45` imports `tiktoken`, LangChain splitters/documents, all document loaders, web-loader helpers, and the selected vector connector. Lines 65-72 import retrieval query helpers; `backend/open_webui/retrieval/utils.py:10-16,40-41` imports LangChain retrievers and Hugging Face Hub. The route module is imported eagerly by `main.py:55-85` and transitively by middleware, files and knowledge. A later spike could keep route declarations and request models eager while moving only ingestion/splitting/retriever dependencies into the functions that process files, URLs, or RAG queries. Oracle: same startup route/OpenAPI/auth surface, no new imports during no-provider chat, then unchanged synthetic upload/index/query/delete and web-fetch behavior. Measure cold startup, stabilized idle PSS, and first ingestion/RAG latency separately. Risks: a dependency exception moves to the first affected request; route setup or cross-module imports may depend on symbols currently initialized at import time; this is broader than the first candidate.

3. **Defer vector-client construction until a vector operation.** `backend/open_webui/retrieval/vector/connector.py:1-26` imports and instantiates the configured backend at module import. It is pulled into retrieval, retrieval utilities, knowledge, and memories (`routers/retrieval.py:37`, `retrieval/utils.py:15`, `routers/knowledge.py:13`, plus memories). A future spike could test a lazy wrapper that constructs exactly the configured backend on the first vector method call, without changing selected backend or configuration. Oracle: startup and no-vector chat readiness/PSS; first vector operation latency; same local collection create/query/upsert/delete, memory and knowledge flows, and identical backend connection failures. Risks: readiness and configuration errors become deferred; concurrent first calls need one safe initialization; clients may have lifecycle/close assumptions; remote vector backends may create connections and require a separately scoped effects test. Do not infer this is responsible for anonymous PSS from the current aggregate report.

## Already guarded paths and stopping point

`backend/open_webui/routers/retrieval.py:106-123` imports `SentenceTransformer` only when a local embedding model is configured and `get_rf` imports reranking implementations only when a reranker is selected. `main.py:686-715` invokes these factories at startup, but empty model settings return without importing those model packages. The source already defers these model weights, so the aggregate torch mapping is not evidence to rewrite this path.

The three candidates are hypotheses only. Before implementation, a separate bounded test should record repeated cold-start and stable idle PSS/RSS, module import traces, request latency, and an ordinary no-provider saved-work journey on the same pinned image/profile. Any candidate must preserve exact routes, authorization, data and provider behavior; report first-use latency and startup-failure changes. No code change, memory reduction, 512 MiB target achievement, energy claim, or architecture/default decision is asserted here.
