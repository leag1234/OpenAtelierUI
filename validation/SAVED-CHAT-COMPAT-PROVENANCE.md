# Private saved-chat compatibility prototype provenance

This is a bounded old-BSD implementation spike for the measured owner-only save/read journey. It uses the existing `Chat.chat` JSON document and `Chat.meta`; it adds no database columns, tables, migrations, dependencies, public/shared routes, or defaults. Only the compatibility `/new` route opts new rows into the namespaced marker; existing clone and shared-copy inserts remain unmarked. The user-visible goal is to save a selected answer path, see the saved item in the owner list, reopen it, and continue. The client and isolated Hardy replay remain primary-owned.

The source27 baseline at `06871d397db85b9d37bcdde25bb68136e541e3ed` preserved the selected chat content, plugin answers, and request payloads, but five selected complete JSON responses failed 99 assertions; the closed-process reopen retained the work while three responses failed 63 assertions. The primary's own-content attribution probe observed that current create/update responses assign message authorship to the authenticated caller, add the caller's profile to user messages, preserve top-level chat ownership, and expose `share_mode: continue` on a subsequent owner read. This is limited to the synthetic private chat. It does not establish shared or historical author identity.

The implementation deep-copies private create/update chat JSON before applying the observed actor attribution to both the history map and flat message list. Owner reads use a separate deep-copy projection that resolves user-message names from the current authenticated caller or one request-local lookup per distinct author ID; it never changes stored JSON or uses message authorship as an access check. The root current-message field is projected from the stored history pointer. A current five-call profile probe found that an account rename does not immediately refresh the current implementation's embedded chat message names. This prototype deliberately resolves the latest names per read to support a clearer saved-work display; it therefore differs from that measured value-level behavior, while preserving the message payload, roles, ownership, and storage bytes. The source-isolated rename test verifies the prototype behavior, not current-runtime parity. Added response fields live in `PrivateChatResponse` and `PrivateChatTitleIdResponse` used by the selected private routes; the old shared, import, search, and admin response models remain unchanged. Current optional private response fields receive their observed empty/null defaults. Owner reads use the existing `(chat id, owner id)` lookup before recording a private read time; that write only changes a strictly validated namespaced marker in `Chat.meta`, and leaves `chat`, `user_id`, and `updated_at` alone. The default owner-list projection reads `last_read_at` from that marker and supplies the measured `active: false`, `archived`, and `snippet: null` fields. Only the exact validated marker is hidden from `meta`; unrelated metadata and unrecognized marker-shaped data are retained. The marker payload is far below the provisional 1 KiB cap.

`backend/open_webui/test/test_saved_chat_compat.py` executes the checked-in normalization, metadata, projection, storage, list, and route functions with controlled stubs. It covers branch/current-pointer preservation, caller attribution, deduplicated profile fallback, marker JSON roundtrip, collision preservation, owner-filtered read writes without timestamp/content mutation, list projection, and denial before read projection or update effects. It also verifies the marker is opt-in to `/new`, leaving the shared clone insertion path unmarked. The insert test extracts and validates with the actual `ChatModel` Pydantic class on both marked and unmarked branches, confirming omission preserves its `{}` meta default. A pre-stage review caught an earlier `meta=None` regression in the unmarked branch; the implementation now omits that key. These tests do not replace a real database/runtime replay. The primary's closed current SQL probe separately found that successful owner reads advanced read time without changing content, owner, or `updated_at`, and denied unrelated/anonymous read and update attempts left every chat row column unchanged; the candidate SQL/runtime replay remains primary-owned.

The checked-in private form accepts null/empty default `variables`, but rejects nonempty variables and non-null folder inputs with422 before storage because this spike cannot safely preserve or locate them in the tested journey. Shared/public chats, legacy historical authors, content-bearing list snippets, active socket state, and the broader list query controls are not qualified. The owner list retains the old candidate's existing archive/folder/pin filters and ordering. The current one-row oracle does not prove larger-history pagination or sorting parity. Marker collisions with an existing, unrecognized meta value remain owner-readable and unmodified; boolean `true` is not accepted as integer marker version1. No migration or attempt is made to invent a past read time or message author.

Source-isolated checks passed for this patch: `python3 backend/open_webui/test/test_saved_chat_compat.py` (18 tests), plus source27 admission (5), plugin-user compatibility (6), importer (23), imported-history (15), flat-group API (8), exact membership (2), and explicit grants (10). Initial isolated test runs failed because the AST test harness stripped optional defaults and omitted a query-column stub; those harness defects were corrected, and the named final suites pass. The primary also reported its reference-current SQL oracle as8 HTTP calls/10 assertions: allowed owner reads persisted read time while leaving content, owner, and `updated_at` unchanged; denied reads/updates left every chat column unchanged; unrelated meta survived. That is reference-current evidence, not candidate-runtime proof. The cumulative regression suites are retained because this branch carries those earlier slices. The primary still owns whole-response assertions, exact source preservation, candidate live SQL behavior, and the closed-process candidate replay. No UI, macOS/Windows, production migration, scale, race/crash, or durable storage-architecture claim follows from this spike.

The earlier stage26 admission commit `20f9241955b80b4b265986565cf97f25ad452fdb` remains retained with its failed runtime evidence; source27's corrective commit `06871d397db85b9d37bcdde25bb68136e541e3ed` fixed the wrong bypass import. This saved-work patch neither amends nor changes that admission slice. The source27 profile measured a 19.26 ms candidate and 38.73 ms reference p95 over only five selected requests; this new implementation has not been timed. The 100 ms selected-path budget remains provisional, and no energy or general performance claim is made.
