# Private saved-chat compatibility prototype provenance

This is a bounded old-BSD implementation spike for the measured owner-only save/read journey. It uses the existing `Chat.chat` JSON document and `Chat.meta`; it adds no database columns, tables, migrations, dependencies, public/shared routes, or defaults. Only the compatibility `/new` route opts new rows into the namespaced marker; existing clone and shared-copy inserts remain unmarked. The user-visible goal is to save a selected answer path, see the saved item in the owner list, reopen it, continue, and explicitly acknowledge read state. The client and isolated Hardy replay remain primary-owned.

The source27 baseline at `06871d397db85b9d37bcdde25bb68136e541e3ed` preserved the selected chat content, plugin answers, and request payloads, but five selected complete JSON responses failed 99 assertions; the closed-process reopen retained the work while three responses failed 63 assertions. The primary's own-content attribution probe observed that current create/update responses assign message authorship to the authenticated caller, add the caller's profile to user messages, preserve top-level chat ownership, and expose `share_mode: continue` on a subsequent owner read. This is limited to the synthetic private chat. It does not establish shared or historical author identity.

The implementation deep-copies private create/update chat JSON before applying the observed actor attribution to both the history map and flat message list. Owner reads use a separate deep-copy projection that resolves user-message names from the current authenticated caller or one request-local lookup per distinct author ID; it never changes stored JSON or uses message authorship as an access check. The root current-message field is projected from the stored history pointer. A current five-call profile probe found that an account rename does not immediately refresh the current implementation's embedded chat message names. This prototype deliberately resolves the latest names per read to support a clearer saved-work display; it therefore differs from that measured value-level behavior, while preserving the message payload, roles, ownership, and storage bytes. The source-isolated rename test verifies the prototype behavior, not current-runtime parity. Added response fields live in `PrivateChatResponse` and `PrivateChatTitleIdResponse` used by the selected private routes; the old shared, import, search, and admin response models remain unchanged. Current optional private response fields receive their observed empty/null defaults. New compatibility rows initialize the exact validated namespaced marker's read time to the row's `created_at`. GET obtains the owner-filtered row and performs only the existing deep-copy response projection; it does not update storage. The default owner-list projection reads `last_read_at` from the marker and supplies the measured `active: false`, `archived`, and `snippet: null` fields. Only the exact validated marker is hidden from `meta`; unrelated metadata and unrecognized marker-shaped data are retained. The marker payload is far below the provisional 1 KiB cap.

An explicit bodyless `POST /read`, declared before the generic `/{id}` route, now acknowledges only the verified caller's fresh marker-bearing private rows. The model selects only row ID, metadata, modified time, share ID, and folder ID; it validates every selected row before issuing any update, preserves unrelated metadata, and writes each marker's `last_read_at` from that row's existing `updated_at`. All updates use one transaction and conditional owner/metadata/timestamp/private-state predicates. Empty owner lists return the measured zero-count shape. Unmarked, invalid/unrecognized marker-shaped, shared, folder-backed, or malformed owner rows cause an explicit conflict before any writes. An exact-shaped pre-existing collision at the reserved marker key is indistinguishable from a marker created by this prototype; it remains a blocker for broad import/adoption, and this slice does not claim universal collision detection. GET is storage-read-only. Title-only private POST preserves `updated_at`; full-chat private POST advances `updated_at` and preserves the read marker. This behavior remains a bounded model/test prototype; the primary owns actual SQL validation.

`backend/open_webui/test/test_saved_chat_compat.py` executes the checked-in normalization, metadata, projection, storage, list, route, and update functions with controlled stubs. It covers branch/current-pointer preservation, caller attribution, deduplicated profile fallback, marker JSON roundtrip, collision preservation, no-write GET, marker creation at `created_at`, private title-only timestamp preservation, full-chat timestamp advancement, owner-filtered read acknowledgment, per-row acknowledgment stamps/count, refusal before writes for legacy/collision/shared/folder rows, empty owner lists, rollback on a conditional-update miss, list projection, and denial before read projection or update effects. The read-ack model tests use a controlled fake query/update DSL and are simulations, not SQLite or application-runtime proof. It also verifies the marker is opt-in to `/new`, leaving the shared clone insertion path unmarked. The insert test extracts and validates with the actual `ChatModel` Pydantic class on both marked and unmarked branches, confirming omission preserves its `{}` meta default. A pre-stage review caught an earlier `meta=None` regression in the unmarked branch; the implementation now omits that key. The corrected current oracle found that GET after creation and after acknowledgment changes no Chat column; explicit acknowledgment updates owned rows to their respective `updated_at` values and does not change other owners. The earlier report that GET advanced read time was incorrect: arbitrary integer normalization masked the unchanged timestamp. That claim and the earlier read-lifecycle qualification are withdrawn. Primary owns the candidate SQL/runtime replay.

The checked-in private form accepts null/empty default `variables`, but rejects nonempty variables and non-null folder inputs with422 before storage because this spike cannot safely preserve or locate them in the tested journey. Shared/public chats, legacy historical authors, content-bearing list snippets, active socket state, and the broader list query controls are not qualified. The owner list retains the old candidate's existing archive/folder/pin filters and ordering. The current one-row oracle does not prove larger-history pagination or sorting parity. Marker collisions with an existing, unrecognized meta value remain owner-readable and unmodified; boolean `true` is not accepted as integer marker version1. No migration or attempt is made to invent a past read time or message author.

The initial saved-work slice passed the primary's source28 frozen replay for its then-covered create/update/list/read response fields and storage checks; that replay did not detect read lifecycle semantics because the comparison normalized every `last_read_at` integer. Its whole-response counts are retained as limited historical evidence, not read-lifecycle qualification. The correction is based on the primary's 0.12.4 ten-call SQL oracle and has source-bound tests only; candidate SQL/runtime validation remains pending. Older carried suites passed before this correction and require a fresh rerun. The primary still owns exact source preservation, candidate live SQL and current API behavior, and closed-process replay. No UI, macOS/Windows, production migration, scale, race/crash, or durable storage-architecture claim follows from this spike.

The earlier stage26 admission commit `20f9241955b80b4b265986565cf97f25ad452fdb` remains retained with its failed runtime evidence; source27's corrective commit `06871d397db85b9d37bcdde25bb68136e541e3ed` fixed the wrong bypass import. This saved-work patch neither amends nor changes that admission slice. The source27 profile measured a 19.26 ms candidate and 38.73 ms reference p95 over only five selected requests; this new implementation has not been timed. The 100 ms selected-path budget remains provisional, and no energy or general performance claim is made.
