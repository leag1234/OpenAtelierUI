# Inactive session-state SQLite spike provenance

This is a bounded, inactive component experiment for `TASK-OPENATELIER-SESSION-STATE-SPIKE-001`. It does not modify the application authentication models, JWT issuance or validation, routes, importer, or defaults. No real accounts, credentials, signed tokens, or raw epoch values were used in the local tests. Fixtures use synthetic account labels and inert password placeholders.

`backend/open_webui/utils/session_epochs.py` is an independently authored BSD-3-Clause module using only Python's standard library. Its explicit copy-preparation command accepts a closed old-format SQLite file and a fresh output path. It verifies the source schema and integrity, requires `auth.id` to be its sole declared primary-key column while accepting text-like declarations such as `TEXT` and `VARCHAR(255)`, limits input to 16 MiB and 1,000 account rows, copies bytes, adds `auth.session_stamp TEXT` only to the copy, verifies integrity and source hash, and publishes without overwriting an existing target. Operations repeat the identity-schema check on the prepared database before selecting an epoch. It refuses source SQLite sidecars and does not attempt live-database backup, automatic migration, or repair.

The component's `get_epoch`, `issue_epoch`, `validate_epoch`, and `rotate_epoch` functions open an existing prepared database in read/write mode without implicit file creation. Queries select only account ID and session stamp. Issue initializes only an existing NULL stamp and returns an existing valid stamp unchanged. Validation compares the caller-provided expected stamp to the stored value. Rotation uses a bounded SQLite write transaction and a conditional update for one existing account. Missing rows, missing schema, malformed values, corrupt databases, and lock timeouts produce named refusals. The component itself does not validate JWT signatures, expiry, roles, MFA, or identity; future integration must do existing authentication checks first and must not source the stamp from user-editable metadata.

Run the local isolated suite with:

```sh
PYTHONPYCACHEPREFIX=/tmp/bsd-epochs-pycache python3 backend/open_webui/test/test_session_epochs.py
```

Result before the identity-schema correction: 10 named tests passed in 0.203 seconds on the helper host (an earlier corrected run took 0.237 seconds). The first run exposed a test expectation that ordered synthetic account rows incorrectly; the database's lexical order placed `synthetic-other` before `synthetic-owner`. The expectation was corrected and rerun. A follow-up also converted a possible Unicode encoding exception into a named `invalid_epoch_state` refusal. The primary review then found that name-only schema checks allowed duplicate IDs or composite identities. The correction requires a sole `id` primary key before copy preparation and each component operation, and retains `VARCHAR(255)` compatibility. The corrected suite has 13 named tests; it covers fresh-copy/source preservation, unchanged unrelated auth/user/chat fields, stable issuance, targeted rotation and stale-stamp rejection, reopen persistence, missing-user behavior, absent database/schema, corrupt/unknown/already-prepared sources, existing-target preservation, malformed stamps, symlink/sidecar refusal, duplicate IDs without a primary key, composite primary keys, compatible VARCHAR IDs, bounded two-connection lock refusal and recovery after release, and JSON measurement output that omits stamp values. These are local stdlib SQLite tests, not an existing-image or full application test.

The opt-in `measure` command reports per-operation p50/p95/p99 latency, SQLite statement/select/write counts, database bytes, account count, and process peak RSS with platform units labeled. It emits no raw epoch value. Provisional budgets remain those in the task contract: validate p95 at or below 2 ms, issue/rotate p95 at or below 20 ms, and one SELECT for each validation. No profile-specific existing-image measurements have been made by this helper; primary-owned measurements are required before any integration proposal. Test-suite elapsed time is not component latency evidence.

Limitations: this does not establish durable schema or storage selection, production migration, crash/SIGKILL recovery, concurrent multi-process correctness beyond the deterministic SQLite lock case, filesystem behavior outside the tested local filesystem, signed-session invalidation, session/JWT/MFA correctness, or administrator/user API semantics. Restoring a pre-revocation auth database may restore an earlier stamp; recovery handling remains unqualified. No user-facing sign-in error or notification was implemented or tested. No desktop/CLI UX, comprehension, accessibility, energy, or hardware-longevity claim is made. The module is not imported by the app and has no effect until a separately authorized integration.
