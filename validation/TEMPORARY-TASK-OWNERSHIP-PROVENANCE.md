# Temporary task ownership spike provenance

The paired native observation in `TASK-OPENATELIER-TEMPORARY-CHAT-001` found that both the pinned current reference and source73 reject the UI's bare `local` completion ID. Both accept an explicit `local:` task context and return one task acknowledgement, but owner task listing does not expose that task, owner/foreign per-context stop returns 404, and global owner/foreign task stop returns 401. The primary used an exact captured task ID for administrator-only harness cleanup; that is not a user-facing fallback. The two selected following replies succeeded and no saved chat/message row changed. These are bounded synthetic API facts, not a rendered temporary UI or broad privacy claim.

This source74 spike keeps a small volatile `task_owners` map beside the existing active-task registries. `create_task(coroutine, id=None, *, owner_user_id=None)` adds an owner entry only for a nonempty verified-user ID and an ID beginning `local:`. The normal done-callback cleanup removes that entry on completion, cancellation, or failure. When the owner map becomes empty, cleanup clears its backing dictionary capacity so a prior burst does not leave a large empty allocation resident. Calls using the old positional signature and calls with stored IDs remain unbound and retain their old behavior. The main nonstream task path and middleware streaming task path pass `user.id`, which comes from their authenticated request path; submitted form/session identity is not used.

The existing authenticated per-chat task list and stop routes use the owner-filtered helper only for `local:` contexts. A user sees and can stop only active task IDs bound to that same authenticated user, even when different users use the same local context string. Missing owner bindings produce the same empty-list/no-active-stop result as no owned work. Bare `local`, saved-chat owner checks, global administrator-only task routes, acknowledgements, task UUIDs, and cancellation/error handling remain unchanged. No saved chat is introduced, and no owner IDs or task IDs are added to response bodies beyond the already existing owner task-list response.

`validation/test_temporary_task_ownership.py` runs the actual task module plus extracted existing route functions. It checks two users sharing a context, an unbound task, owner-only list/stop behavior, positional-call compatibility, normal/error cleanup, stored and bare-local paths, and both authenticated task-registration call sites. A 1,000-entry cleanup-burst check measured the Python 3.9.6 dictionary at 36,960 bytes before clear and 64 bytes after clear; this measures only the map container on this host, not task memory or total process RSS. `python3 validation/test_temporary_task_ownership.py` passed 6 tests; related regressions passed `python3 validation/test_task_ownership.py` (9), `python3 validation/test_chat_hook_ownership.py` (2), `python3 validation/test_async_plugin_compat.py` (9), `python3 validation/test_chat_metadata_ownership.py` (6), and `python3 validation/test_chat_session_compat.py` (5); `git diff --check` passed. The source change is 37 added nonblank runtime lines, within the 80-line bound.

The map's measured memory footprint and native request cost are not established by these tests. This is a reversible spike only: no durable registry, persistent identity, expiry policy, multiworker/restart recovery, UI behavior, or architecture/default acceptance is claimed.
