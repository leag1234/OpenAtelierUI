# UI identity source change

This source slice connects the supplied OpenAtelierUI artwork to the existing sign-in, navigation, browser and server identity surfaces. The asset archive remains an unchanged user-provided input at `../ui-inputs/openatelierui-logo/`; its SHA-256 is `b2167e21ea463404228d81a07fd9b2ff51440e6838fabd407d37b2cf2b3cc218`. Selected source SVG/PNG files are copied without alteration. The only derived image file is the ICO container described below. No separate artwork license was supplied, so this note does not assign one.

`src/lib/constants.ts` and the backend default the product name to `OpenAtelierUI`. The inherited exact `Open WebUI` label is still mapped to `OpenAtelierUI`, while other configured `WEBUI_NAME` values are retained. The legacy `CUSTOM_NAME` variable remains accepted but no longer contacts an inherited external branding service; operators set `WEBUI_NAME` and `WEBUI_FAVICON_URL` directly. Existing route and protocol names remain in place for compatibility.

The supplied light/dark wordmarks are used on sign-in for the OpenAtelierUI project identity. The home control has an explicit `Home` accessible name in both themes; both visual logo variants are decorative to assistive technology. The large navigation mark uses the supplied light/dark symbol SVG for the project identity. When the resolved application name is custom, sign-in and the large navigation mark retain the old splash-image path and sizing/theme behavior. Onboarding/splash, browser icon, avatar fallback, notification icon and backend PWA icon use the supplied raster symbol.

FastAPI serves `/static/*` from `backend/open_webui/static`. The existing startup copy step syncs the compiled frontend static assets and explicitly recopies the legacy favicon and splash. The new wordmark and dark-symbol paths therefore exist in both `static/static/` and `backend/open_webui/static/`; the fresh frontend build and backend-mounted static tree both contain them. The active dynamic `/manifest.json` route points to the replaced backend `logo.png`. `src/app.html` links that dynamic manifest. The older static `site.webmanifest` and its 192px/512px icons are not linked and remain byte-unchanged.

The browser tab, sidebar fallback, notification and other existing favicon consumers continue to request `/static/favicon.png`. The fixed brand logotype remains independent of a custom favicon. `/opensearch.xml` also retains the configurable favicon path.

The backend static tree contains 66,194 bytes across 12 changed/replaced identity files; the frontend public-static tree contains 56,658 bytes across 11 files. Combined working copies occupy 122,852 bytes before build output, with repeated artwork represented in both trees. Each 609-byte `favicon.ico` contains the supplied PNG32 bytes plus a 22-byte ICO directory/header. The test checks the embedded PNG. No original image was edited in place. An early `sips` trial generated a 5,753-byte 192px resize (SHA-256 `d66b957d7cfef24513df4c7fe6d3617ee9a129f42e7d89b5492739d7a7490352`); primary review identified it as an unused companion and both generated copies were reverted. No derived raster remains.

`validation/test_ui_identity_sources.py` checks default-name resolution, absence of inherited branding-service calls, backend static paths, exact artwork copies, ICO contents, manifest paths and the home-button accessible name. These source checks do not compile Svelte, start the application or inspect rendered pixels. The primary owns the fresh offline build and actual desktop/mobile, light/dark, keyboard and saved-work review. No source-only claim here establishes visual acceptance, human UX acceptance, accessibility conformance, full frontend compatibility or a native MdkLinux identity decision. Original attribution remains in the About surface. No font, dependency or external artwork request was added.

The initial source edit briefly referenced new symbol filenames that the backend did not serve and bypassed the configured favicon path; review corrected those references to the existing runtime paths before commit. An attempt to use the host Pillow extension for ICO writing failed to import. The final ICO was built as a standard single-image ICO header around the provided PNG32 bytes and checked with `file` plus the source test. A static path lookup also initially used the candidate-relative rather than shared ignored asset directory; no user inputs were modified.
